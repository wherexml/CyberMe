## 投递层

`server/src/attention-delivery.ts` 给每个事项一个投递判断。可见性不设预算，打断才设预算。摘要的数字是初始取值，不是实测调参。

| 档位 | 条件 | 主对话 | macOS | 右侧面板 |
|---|---|---|---|---|
| recovery | `send_unknown`、`failed`、未确认的生成或来源处理 | 一行状态 | 无（待原生路由核验） | 决策，直到解决 |
| urgent | 未决请求且 `priority=high`、24 小时内 `dueAt` 或命中现有紧急关键词 | 一句结论 + 动作 | 无（待原生路由核验） | 决策，立即 |
| decision | 其余未决请求 | 摘要行 | 无 | 决策 |
| suggestion | 灵感 | 默认无 | 仅 `alerts=every` 且不在免打扰期间 | 灵感 |
| quiet | 无需动作 | 无 | 无 | 无 |

常规 `sending` 不写主对话，也不发通知，状态只留在事项上；时间再长也不会被判成失败或未知，也不会自动重发。

macOS 通知范围没有扩大：`/api/native/notifications` 仍只选灵感提醒，原生文案和点击路由只针对洞察，核验前不接入请求或恢复项。免打扰期间不提交任何通知，这与 `notificationPreview` 对紧急项返回 `immediate` 不同，以通知页的既有阻止行为为准。

### 设置与单事项策略

现有 `autonomy.alerts` 与免打扰仍是权威，判断复用 `notificationPreview`，不新增全局设置。

- `every`：决策逐条推送，灵感恢复提醒与 macOS 通知。
- `urgent_digest`（默认）：紧急逐条，决策进摘要，灵感安静。
- `digest`：紧急也进摘要。免打扰期间非紧急等待。

单事项 `deliveryStrategy`：`auto`（跟随设置）、`immediate`、`digest`、`quiet`，由 `POST /api/attention/strategy` 写入，详情页用共享分段控件 `seg` 设置（V6 没有现成的共享下拉组件，因此不新造一个）。`quiet` 不隐藏 recovery，也不隐藏决策面板。`immediate` 只影响主对话。

### 摘要与账本

- 事项键：`inbox 根(sourceParentInboxId||id) + requestMessageId`，只用精确 ID，不做标题或来源相似合并。修订取请求消息的 `messageRevision`。
- 账本实体 `attention_ledger` 按 `(事项键, 修订)` 持久记录档位、判断（`chat`/`held`/`digested`/`suppressed`/`attached`）、原因和时间；重启后续用。
- 摘要是 `inboxAnalysis.digest=true` 的派生消息，最多每 3 小时一条、3 行，超出部分只给真实条数并继续等待下一次。每行投递前和每次同步都复核，事项失效就删行，空摘要撤回。
- 文案不超过约 120 个中文字符，草稿与证据只在详情。
- 迁移：已有提醒的文字不改写，只补动作元数据。新规则只作用于新投递。

### 与灵感的关系

灵感必须先有明确的 `requestBinding`（不会仅凭引用自动创建），且证据只有在 `messageId` 与决策当前 `requestMessageId` 相同、且修订相同时才附着到该决策，不单独投递，并从灵感列表移到决策卡下。同根、来源重叠、标题相似或同发送者都不合并、不压制。证据 `messageId` 由服务端按“引用恰好落在一条消息内”确定，多条命中则留空，不附着。

## 消息动作

`shared/attention-actions.ts` 是类型白名单：`draft_reply`、`create_task`、`snooze`、`dismiss`、`discuss`。标签由服务端固定，模型文本不会成为可执行类型，也没有任意执行入口。

- 绑定：`{entityKind, entityId, requestMessageId, requestRevision}` 或 `{provenanceKey}`，服务端复核，不符返回 409 `action_stale` 且无副作用。
- 幂等：`POST /api/attention/actions` 先持久登记 `operationId`；重复请求返回原结果，`GET /api/attention/actions/:id` 回读。重启时未完成的操作记为 `unknown`，不重放。
- `draft_reply` 只生成草稿，不外发、不批准。`discuss` 只走输入框。灵感执行仍走原入口。

## 持久忽略与推迟

| 动作 | 绑定 | 效果 | 何时回来 |
|---|---|---|---|
| 忽略请求 | 现有 `attentionDismissal` | 各面板消失 | 新请求或实质编辑 |
| 清除已结束记录上的新请求或“结束时间待核实” | `attentionAck`（请求 ID + 修订），不改状态和发送回执 | 卡片消失 | 新请求或实质编辑 |
| 推迟请求 | `attentionSnooze`（请求 ID + 修订 + `until`） | 各面板隐藏、投递暂停 | 到期、新请求、实质编辑，或截止早于到期时间 |
| 忽略灵感 | `status='dismissed'` + `attentionAction` | 卡片、提醒、通知、追问上下文消失 | 仅手动恢复 |
| 推迟灵感 | `status='deferred'` + `deferredUntil` | 同上，有时限 | 到期（一条摘要行），或生成器发现新证据（正常提醒） |

撤销：`POST /api/ideas/:id/attention`，`action='undo'`，服务端窗口 15 秒 + 5 秒网络余量。

- 忽略的撤销与消息恢复在同一事务内，先按当前来源跑完整 `support()`。来源变化或不可读时，灵感已恢复，消息仍撤回并按原规则等待复原；其他失败则永久撤回。
- `dismissed` 只有这个精确 `operationId` 的撤销可以复原消息；`user_removed` 永不恢复。恢复不产生新提醒，并写入通知抑制回执。
- 超窗后 `action='restore'` 只恢复卡片。
- 推迟的撤销也只恢复卡片，消息保持撤回。

列表末尾有普通的“已处理”入口，没有计数和横幅。

本地标记：旧 `ui.gal`（暂不处理）不迁移。它继续只在本机隐藏卡片，记录、提醒和通知都不变；在“已处理”里可恢复，或明确点“忽略”后才写入服务端。将来日期的 `ui.brief.later` 迁移一次为同等时长、可撤销的推迟。

## 已结束记录

判断未决且请求消息存在时，展示和转出使用同一判断（`shared/inbox-surfacing.ts`）：

| 情况 | 结果 |
|---|---|

## 时间模型

| 字段 | 含义 | 展示 |
|---|---|---|
| `occurredAt` | 证据消息的发送时间，未知保持未知 | 来源 11月4日 13:18 |
| `deadlineAt` / `scheduledAt` | 逐字引用校验过的 `events[]`，`basis` 为 `stated`/`inferred` | 截止/安排 …（来信写明/推算）；已过显示“结果未知” |
| `surfacedAt` | 消息 `createdAt` | 推送 00:37 |
| `refreshedAt` | 灵感更新时间，不代表来源新鲜 | 更新 … |
| `checkedAt` | 打开详情时只读比对当前来源指纹，不写入记录 | 核对于 … · 来源未变化 |
| `sourceUpdatedAt` | 引用来源的最新事件时间，带时区才显示 | 来源最新 … |

- 模型按消息拿到 `{id, sentAt, sender, actor, body}`，并且总是保留最新消息；预算按从新到旧累计，来源指纹不变。
- 新鲜度和提醒判断使用证据消息时间，聊天缺少证据时间时保持未知；无关新消息不会让旧证据变新。
- 截止已过且无结果：提醒以 `event_passed` 撤回，卡片显示“已过期，结果未知”，灵感状态和底层工作都不变。

## 面板

- 决策页：恢复项、未决请求、待确认请求。灵感页只放灵感。
- 卡片结构：类型 · 来源 · 来源时间，一句结论，一行理由，有数据才画的时间条，动作。
- 只有存在已校验截止或至少两个不同事件时间才画时间条；没有依据就不画，不填占位指标，也不再用优先级推出“今天”。
- 发送者读 `senderName`，兼容 `sender`/`from`。
- 详情按数据显示，缺数据的块不出现：灵感时间条（来源时间 + 已校验截止或安排）；更新前（`idea_history` 中标题或正文确有不同的最近一条，`GET /api/ideas/:id/facts`）；会话时间线（精确请求 ID 且至少两条带时间的消息）；关联任务（`inboxId`、`sourceInboxId`、`ideaId`、`sourceIds` 精确匹配，显示真实状态）。

## 本机合并前补记（2026-11-06）

- 同一消息含两个事项时，仅相同 messageId/修订不能认定同一决策；无明确 requestBinding 的灵感保持独立可见。
- 同一 operationId 改换 snooze 的 until 必须冲突，不得被当作同一操作静默接受。
- 合并保留并行的 actor、人物资料指纹、24 小时触发证据窗口和逐条 messageId 校验；不以容器最近活动替代证据时间。
