# 持续 Agent 的消息追加

## 行为

2026-11-11：每个 conversation 沿用同一个持续 AgentSession。普通新交办进入持久输入列表，当前工作继续，随后顺序处理。开头明确使用「补充／更正／纠正」等标记的直接输入，在当前工具批次结束、下一次推理前读入同一工作；不明确的换题保持普通顺序。引用、代码块中的标记不触发提前消费。发送本身不调用 abort；旧显式 interruptCurrent 接口仍只承担明确打断的兼容行为。

不增加发送模式选择器、说明卡片或次要标签；不因追加消息自动创建产品任务。

## 持久输入与消费

- `chat_requests` 是回执及调度的事实来源。`chat-inputs.ts` 为每个会话维持一个消费循环，SDK 内存队列仅承担投递。旧 continuation 接口复用该输入流，`chat_queue` 只保留兼容元数据，不再启动第二个 worker。
- 接收先保存用户消息和 queued 回执，HTTP 202 只表示已登记。普通请求处理完后，消费循环启动下一条并复用同一 SDK 实例。
- 提前消费的补充仍有自己的 requestId 和 runId，通过 parentRunId 关联原工作。`claimedAt` 表示准备开始，`consumedAt` 仅在 SDK 真正开始接收该条追加消息的事件上写入；二者均不代表任务完成。
- 同批选定资料、附件和追加原文按顺序进入同一 SDK 推理边界；原文保留独立条目和来源归属。一个助手回复可以关联多条输入，界面保留中间及最终文本，不重复生成气泡。
- 每个原工作最多提前接纳八条补充（含准备失败的条目），其余持久保留并由下一轮继续处理。同一 conversation 保持一个 AgentSession，不另建子 Agent。

## 权限、来源、成果与超时

- 当前工具批次结束后才增加新的权限绑定。每条输入单独构建 readOnly、直接交办原文、凭证引用及工具；带 evidence 的操作按原文匹配其授权输入。工具在自己的 run 下留下回执，不因同会话复用获得别条消息的写权限。
- 普通后续请求在出队时加载资料；提前消费的补充在准备边界重新加载选定来源和附件。已移除来源明确失败，不影响原工作及其他输入。全局记忆规范保持不变。
- 上传图片字节只存在当轮上下文，持久副本及轮末沿用脱敏；来源追溯与忘记传播涵盖追加原文及其派生回复。
- 普通/深度处理预算分别为 110/150 秒。补充开始准备时获得新的有界预算，避免继承即将到期的旧计时器；每个原工作最多接纳八条，不能通过不断提前追加无限延长该原工作。工具单次时限与模型传输时限仍有效。
- 实际生成的文件按输入登记，最终消息保留附件，原请求与补充各自的 taskOutcome 依据自己的工具证据。模型回复成功不等于业务操作完成；未知写入与 partial 仍需核对，不自动重放。

## 兼容与恢复

GET `/api/chat/requests/:id` 保留旧字段，增加可选 delivery、claimedAt、consumedAt、parentRunId。已存在请求的指纹不迁移；新请求仅显式传 appendDelivery 时才把它纳入指纹。

旧 `POST /api/chat/continuation` 的 steer/queue 分别适配为提前补充/普通追加，接收时返回 queued。兼容回执的 inserted 只在实际进入原工作后出现，并通过 processingStatus 额外报告真实处理状态。编辑、取消、版本冲突和重复提交都针对同一份待处理输入，不双消费。

刷新、断网和迟到响应只回查原 ID；服务重启对 running/queued 留下失败或 partial，不自动重放。尚未开始的请求可显式重试；已开始的未知副作用保留人工核对边界。
