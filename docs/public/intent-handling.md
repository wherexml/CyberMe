# 意图处理与用户注意力

本页对应 `shared/inbox-attention.ts`、`shared/inbox-surfacing.ts`、`server/src/inbox-attention-actions.ts`、`server/src/inbox-triage.ts`、`web/src/v6/attention.ts`、`web/src/v6/model.ts` 与 `web/src/v6/Brief.tsx`。复验入口见文末。

## 修改前失败清单（2026-11-05）

系统不确定性被直接当成用户任务：

1. 系统联系人变更通知、营销、普通闲聊、已解决讨论在简报「灵感」里变成「来源已变化」卡片。根因：`insightOf` 把每条 `verify` 记录都映射成卡片，且 `/source|time|context/` 把来源、时间、上下文一律称为“已变化”。
2. 缺少消息时间（`time_unknown`）或后台判断失败（`judgment_failed`）单独就会产生待处理卡片，即使判断结果明确无需处理。
3. 「重新核对来源」和「忽略」都只把文字填进输入框，还要再按一次发送，由模型决定；没有持久状态，也没有忙碌、失败和撤销反馈。
4. 卡片摘要直接取 `item.body`，可能露出容器摘要或原始 JSON。
5. 决定卡默认选项“不需要回复，标记为已处理”同样只是聊天指令。

忽略后的回潮：

6. 已忽略事项收到无关新消息后，来源版本变化使判断失效，`changedClosed` 立刻把它转回 `verify`，于是再次出现卡片。
7. 忽略没有绑定请求身份；只比较时间戳。来源回填的较早新请求会被永久压制，同一旧请求的时间异常又可能复活。
8. 简报决定卡的本机标记（`ui.brief[id]`）让已结束事项继续占位；“稍后决定”到期后，安静事项会以待决定卡片重新出现。
9. 灵感和主对话提醒只看灵感自身状态，来源事项全部已忽略或已完成后仍可能再次出现。
10. 在途草稿生成完成后写入 `status:'pending'`，把生成期间的忽略覆盖掉。

保护不足：

11. 来源变化使判断暂时失效期间，未解决的重要请求从简报消失；判断再失败时没有任何可见线索。
12. 判断失败后没有有界重试，只有再次变更来源才会重算。

## 本地评审补充失败清单（2026-11-05，第一轮）

更正：上文第 10 条的成因判断有误。`adoptionState` 已包含 `status`，生成期间被忽略时结果走候选稿路径，不会写入 `status:'pending'`。之前为此加的 `drafts.ts` 改动是无效代码，已撤回；现由 E2E 固定该行为。

13. `server/src/ideas-chat.ts` 的 `id` 隐式 any，类型检查失败。
14. 「重新判断」只要 HTTP 成功就显示完成。`/triage` 判断失败也返回 200 和 `status:'failed'`，`process-source/retry` 只是排队，都被说成已完成。
15. 简报新增的统计行违反“不加说明和统计文字”的界面约束；已忽略事项逐条显示 24 小时，在两个子标签里又形成一个队列。
16. 绑定只记消息 ID：已忽略的通知被原地编辑成明确请求后，因 ID 相同被永久压制。
17. 同一消息再次编辑时，轮次 ID 只由消息 ID 决定：已结束的轮次会挡住新请求，放开后又可能重复建轮次或复用旧发送键。
18. `ideaSourcesClosed` 只看容器状态：来源仍显示已忽略，但其上有待处理的新请求或判断未定时，新灵感被误隐藏。
19. 生成完成晚于忽略、同发送者反馈使判断失效，这两种情形没有可重复验证。
20. 浏览器脚本使用 `process.cwd()` 和未创建的 `p2` 页面，产物路径和页面都不可靠。

## 必须保持的行为

- 判断成功且低风险的 FYI、无需动作、已解决内容不进入简报，也不需要用户忽略。
- 单凭时间缺失或判断失败，不产生用户卡片；系统状态不在简报显示，诊断留在完整收件箱和设置。
- 未解决的重要请求、敏感决定、待批准、人工草稿和候选稿、`sending`、`send_unknown`、发送失败和执行恢复都不能隐藏。
- 原始记录和诊断继续留在完整收件箱。`inboxDisposition` 的 `verify` 投射保留给诊断，不再等于用户任务。
- 不伪造成功判断，不用营销关键词当证据。
- 简短明确的请求是请求；长对话本身不构成事项。
- 承诺要做、生成了建议或任务，都不等于已完成；“已解决”只来自带精确回复证据的 `resolution:'replied'`。

## 四层事实

| 层 | 字段 | 含义 |
| --- | --- | --- |
| 来源证据 | `messages`、`sourceAttachments`、`inboxTriageVersion` | 实际收到的内容，不可信，绝不构成授权 |
| 业务判断 | `inbox_triages`（`resolution`、`actionType`、`requestMessageId`、`replyMessageId`） | 模型或规则判断，带版本；用户指示、第三方请求和 AI 建议保持为不同事实 |
| 用户注意力 | `inboxAttention(item)`（只读投射）、`attentionDismissal`（持久） | 现在是否要占用用户注意力 |
| 执行与授权 | `status`、`approved`、`receipt`、发送账本 | 只由真实发送、回读和批准路径更新 |

不新增任务库或长期目标平台。注意力是从现有记录计算出的投射，只有“用户忽略”这一事实新增持久字段。

## 注意力投射

`inboxAttention(item)` 由服务端和界面共用，服务端随事项返回只读 `attention`。

| `state` | 含义 | `surface` | 界面 |
| --- | --- | --- | --- |
| `actionable` | 有证据的决定或请求 | `decision` / `insight` | 决定卡或原因明确的灵感卡 |
| `execution` | 发送或生成处于恢复状态 | `insight` | 原因明确的卡片；未知结果不可忽略 |
| `reevaluating` | 后台正在或等待判断 | `none` | 不显示 |
| `system_error` | 判断或处理失败 | `none` | 不显示，诊断在完整收件箱 |
| `quiet` | 已安静解决或已忽略 | `none` | 不显示 |

判定顺序：执行恢复 → 已结束 → 待处理 → 人工草稿与批准 → 敏感 → 判断缺失或失败 → 有判断时看证据。

“有证据”指判断成功且满足其一：`resolution:'open'` 且动作为 `reply`/`decision`；`needsReply`、`needsOwner` 或 `risk` 不低于 0.75；优先级为 `high`。其他成功判断不占用用户注意力。

缺少关键私有信息时：记录自身带 `v6.question` 才显示具体问题；否则显示按判断原因选择的简短状态（如“缺少所需资料或附件内容”），不编造问题，也不显示原始 JSON。

判断失效期间，服务端用上一次成功判断中精确的未解决请求生成只读 `lastOpenRequest`。若该消息仍存在且未删除、未撤回，事项继续保留，具体状态按下节区分。

### 判断未成功与未定位请求（2026-11-18）

失败面（合成示例）：

- A：事项有 `lastOpenRequest`，当前判断 `status:'failed'`、`route:'review'`、`attempt:3`，没有 `nextRetryAt`。旧界面仍显示“正在重新判断”，卡头写待回复，决策卡还按失败判断的 `route` 推荐“起草回复”。实际不会再自动重试，起草也会被服务端以 `draft_judgment_required` 拒绝。等待自动重试的卡同样仍提供起草。
- B：多条聊天消息，判断成功但 `resolution:'unknown'`、没有 `requestMessageId`、草稿为空。因没有选中请求而没有请求时间，旧界面显示“消息时间待核实”，误报时间问题。
- C：旧版已将 `draft_judgment_required` 保存为操作拒绝，重新打开同一条请求时，当前判断状态下仍出现旧红色错误，甚至在判断成功后继续显示。复验须覆盖等待、判断中、失败和成功恢复，同时保留原拒绝回执及真实未知结果。
- D：原生窗口点击「重新判断」时若已有在途读取，完成回执可能和「正在重新判断」同时出现，起草入口要等下一次轮询才恢复。完成回执应在更新后的读取返回后再显示。

规则（`shared/inbox-attention.ts`，界面 `web/src/v6/model.ts`、`Brief.tsx`、`MessageActions.tsx`）：

- 绑定旧请求（`lastOpenRequest`）而当前判断未成功时，一律保持 `reevaluating_open` 和决策面，提醒、附着灵感、回执和投递语义不变。`detail` 如实区分：`running` 正在重新判断；`retry_scheduled`（`nextRetryAt` 存在且 `attempt` < 3）判断失败，等待自动重试；`failed` 判断失败，待重新判断；`pending` 等待判断。
- 判断未成功（共享 `judgmentUnsettled`）：卡头不写待回复/待决策，任何选项都不标推荐，旧 `v6.options` 不使用。起草行按优先级显示：进行中或未确认的回执（可核对）→ 当前未过期草稿（查看草稿）→ `failed` 时「重新判断」（`POST /triage`，`force:true`，显示结果并回读）→ 其他情况只在卡头显示判断状态。
- 新起草要求当前判断成功、事项在待处理中且动作为回复；主对话历史提醒也遵循这项要求，保留回执核对和查看草稿；详情只在判断成功时提供新的「起草回复」。
- 同一事项进入重新判断，或已有晚于起草操作的新判断时，卡片、详情和主对话停止重复显示旧的 `draft_judgment_required` 拒绝。保留原操作编号和状态，未知结果仍走原编号核对。
- 「重新判断」返回后读回一份新的工作区快照。已有较早的读取在途时，等待其结束再读回，随后显示完成回执。
- 判断成功、没有 `requestMessageId`、聊天中有消息且仅缺时间：`request_unlocated`，显示“未定位到具体请求”，保留查看详情，不用最近消息当作请求，也不显示来源时间。确有选中请求而时间无效，或没有消息时，仍显示“消息时间待核实”。
- 卡片直接显示已有草稿正文摘要（旧草稿单独标注）；可回复的成功判断仍走「查看草稿」/起草的正常流程。

隔离复验使用 `scripts/reply-card-judgment-fixture.mjs`（文件头有构建与启动命令）和 `scripts/reply-card-judgment-browser-e2e.mjs`。在 ego-browser 选择的 TaskSpace 中注入 `spaceId` 及绝对路径 `outputDir` 后运行浏览器脚本，得到判断失败、未定位请求、草稿正文截图和 `browser.json`。可以用 `CYBERME_REPLY_FIXTURE_ASSETS` 指定构建桌面包时嵌入的网页资源。模型使用受控响应，服务端走生产 HTTP 和隔离 SQLite。测试从旧拒绝回执进入，复现较早工作区读取与重新判断重叠，核实一次重新判断、一次草稿持久化和零发送。

源码和桌面包网页资源各通过 15 项浏览器检查，意图处理 HTTP 129 项、注意力动作 HTTP 28 项通过。隔离 MyGO 窗口使用同一组网页资源，实测重新判断后恢复起草、显示待确认草稿，发送账本为零。

## 忽略与撤销

- `POST /api/inbox/:id/attention-dismissal`：`{operationId,baseUpdatedAt}`。复用规范状态 `status:'dismissed'`，经典界面和 V6 读取同一字段，不是本机标记，也不经过模型。
- `POST /api/inbox/:id/attention-dismissal/undo`：`{dismissalId,baseUpdatedAt}`。
- 同一 `operationId` 或已撤销的同一 `dismissalId` 重放返回 `replayed:true`，不重复写入。
- 版本不符返回 409 `edit_conflict`；界面刷新后由用户决定。
- `sending`、`send_unknown`、`sent`、`delivered`、`recalled` 和结果未知的草稿生成不可忽略（409 `dismiss_blocked`）；已完成事项返回 409 `already_closed`。
- 撤销只恢复 `status`、`closedAt` 和绑定字段，保留此后写入的消息、草稿和批准。忽略已被替换（`dismissal_superseded`）或新请求已转出独立轮次（`dismissal_forwarded`）时拒绝。撤销不设置 `attentionOverride`，事项回到注意力投射本来的位置。
- 经典界面和 Agent 工具的 `PATCH status` 写入同样的绑定，不产生第二套状态。
- 忽略一件事只产生同发送者的弱反馈，不屏蔽发送者。
- 忽略成功后，简报只显示一条撤销确认，15 秒后自动消失，新的忽略会替换旧确认。确认只存在于当前页面，刷新后消失，已忽略状态不变。更早的事项在完整收件箱重新打开。

## 绑定与重新进入

`attentionDismissal` 记录 `{id,operationId,requestMessageId,sourceVersion,knownMessages,priorStatus,priorClosedAt,dismissedAt}`，由服务端管理，客户端写入返回 403。`knownMessages` 是消息 ID 到语义修订值的映射。修订值只取正文、回复与线程关系、提及、附件标识和删除撤回状态，不含头像、显示名、发送方向和同步时间。不使用关键词判断。

| 忽略后的情况 | 结果 |
| --- | --- |
| 判断仍指向同一请求或忽略时已知的消息 | 保持已忽略 |
| 无关新消息，判断尚未完成 | 保持隐藏，判断状态留在完整收件箱 |
| 无关新消息，判断为无需动作 | 保持已忽略 |
| 判断指向未知的新请求（`resolution:'open'`，有精确消息 ID） | 建立独立轮次，旧事项和它的发送键不变 |
| 同一消息只有元数据变化 | 保持已忽略，不建轮次 |
| 同一消息内容被实质编辑，重新判断后为未决请求 | 建立独立轮次；判断前保持隐藏 |
| 已转出的同一消息再次编辑，且该轮次仍未结束 | 不建新轮次，由原轮次同步并重新判断 |
| 已转出的同一消息再次编辑，且该轮次已结束 | 按新修订值建立新轮次，不带草稿和发送键，已结束轮次不变 |
| 新消息到达，判断为不可识别请求但回复需求不低于 0.75 | 作为“新请求”重新显示，不永久压制 |
| 判断失败 | 不复活卡片；错误留在完整收件箱 |

没有绑定记录的历史已忽略事项沿用原有时间比较；没有可用结束时间时只显示可清除的“结束时间待核实”，不转出（见[注意力投递](attention-delivery.md)）。

## 后台重算

沿用 `startInboxTriage`：每轮最多一条、同事项进程内合并（`inflight`），版本不符的结果不采用（`triage_source_changed`），冷却和读取权限不变。读取界面不会触发模型调用。

失败重试有界：同一来源版本最多 3 次，间隔 5 分钟、30 分钟；额度不足、未配置和上下文过长不自动重试；历史失败记录不补重试。来源版本变化重新计数。

详情中的「重新判断」直接调用 `POST /api/inbox/:id/triage`（`force:true`），资料处理失败时调用 `process-source/retry`，并按响应内容显示结果：只有判断 `status:'succeeded'` 才显示完成；判断 `failed` 或任务 `blocked` 显示失败原因；`queued`、`running` 显示已排队或处理中；其他状态显示结果未确认。「深入讨论」仍是对话入口，只附上记录、不自动发送。不自动发送、不自动批准、不重放未知外部结果。

## 第二入口

- 决策卡的本机标记不能让已忽略事项回来；只有已选择并已发送的记录保留结果卡。
- 灵感的 `sourceIds` 全部精确指向已结束的收件箱事项时，不进入灵感列表和主对话提醒。“已结束”要求事项状态已结束、注意力投射确为 `quiet`，且没有未结束的转出轮次。判断待定、判断失败、有新请求或已撤回的来源都不算已结束。这只是展示抑制，不把灵感标记为完成。
- 来源混合（含任务、记忆或未结束事项）时保留。

## 已知边界

- 每个收件箱事项只有一个当前请求（`triage.requestMessageId`）。同一会话里同时存在多个独立请求时，模型只选一个，其余要等它解决后才显现。本轮未实现任意多请求提取。
- 反馈写入 `dismissalFeedback`，属于判断版本的一部分，所以忽略或撤销会让同发送者其他事项重新判断一次。这是既有机制；改变它会使所有已存判断失效，本轮未动。`lastOpenRequest` 保证重算期间未决请求不消失，并留在决策面（2026-11-05 起，见[注意力投递](attention-delivery.md)）。
- 没有修订值的历史轮次视为已覆盖该消息，不因再次编辑建新轮次。
- 无 API Key 且不走本地模型的事项会一直处于等待判断；简报不显示这类系统状态，完整收件箱仍可查看。
- “不可识别的新请求”依赖模型给出的回复概率，判断质量仅经少量真实消息抽样，未完成全量评估。

## 本机复核补充失败面（实现前）

- 旧记录或经典 PATCH 将生成结果未知的事项标为已忽略后，不能让未知生成从简报和核实入口消失；经典与 V6 必须共用忽略阻断，历史已关闭记录仍保留未知结果恢复。

- 长列表底部点击忽略后，15 秒撤销提示不能留在滚动区域上方而不可见；提示应保持在当前滚动视口内，且仍只有一条。

- 重新判断失败时，不向用户展示模型供应商、HTTP 状态和内部错误原文；界面保留可重试的简短错误，诊断留在完整记录。

## 2026-11-06 请求轮次固定绑定

失败场景：会话同步给多个历史轮次复制相同消息后，重算没有限制 `requestRoundId`，旧轮次和新轮次同时选中最新来信，产生重复决定卡。

- 轮次仅判断原始 `requestRoundId`；后续消息仅作为解决该请求的上下文。私聊、群聊共用绑定约束，群聊无关回复仍不能关闭原请求。
- 模型候选只能包含该消息；原请求缺失、撤回、删除或超出有界上下文时失败待核实，不改绑新消息，不伪造完成。

- 现有错绑记录通过重新判断恢复，保留原消息、事项、草稿及回执；无需回复或已回复退出决定列表，不批量删除记录、不产生发送。

## 2026-11-12 类型化动作的可靠恢复（洞察卡、消息动作、详情）

实现前失败场景：

- 请求或回读丢失后忘记原操作 ID，再次点击用新 ID 再跑一次模型（`draft_reply` 服务端不按请求版本去重）。
- 卡片、消息动作和详情各有独立锁；切换标签、重载页面或原生重启后丢失进行中/未确认状态。
- 本机保存失败仍然提交；清理记录时丢掉未决操作或无关草稿。
- 把 GET 404、5xx 或“规范记录里看不到效果”当作“未执行”，迟到的原请求或中断的操作因此重复。
- 来源变化后清掉旧的未决操作，或用旧操作的成功把新请求标成已完成。
- 过期或容量上限静默删除未决操作 ID。
- 把旧请求关联的任务当成当前请求的任务；把“已创建任务”说成工作已完成。
- 详情把旧草稿或候选草稿标成普通回复草稿，并用单独的 `/draft` 请求路径绕过共享状态。
- 渲染、聚焦或回读自动提交、外发或调用模型。
- （复核补充）提交请求无传输超时，挂起的响应让回读永远被阻止；轮询达到上限后按钮一直显示忙碌；对已可能执行的操作重试时本机保存失败，被错误地标成“未提交”；以可能已被取代的 `draftPreparation` 作为证据；消息下的「展开聊聊」被当成类型化动作提交（服务端明确拒绝 `discuss`）；详情对无绑定记录保留单独的直接 `/draft` 请求路径。
- 窄屏/深色/英文控件或输入框回归；页脚与冷却等待丢失。

规则（`web/src/v6/attention-action-state.ts`，数据契约见 [V6 数据与草稿契约](v6-data-contract.md)）：

- 每个“对象 + 动作类型”一个回执槽，卡片、派生消息和详情共用。提交前先把操作 ID、类型、绑定和不可变输入（如 `until`）写入本机 UI 状态并 `durable()` 成功；保存失败不发请求，显示「未保存，未提交」，可明确重试同一 ID。
- 结果：2xx `succeeded` 记为成功回执；明确拒绝（除 408/429 外的 4xx，带错误码）记为拒绝并照常显示；`inbox_cooling` 仍是中性冷却等待；无状态码、超时、408/429 和 5xx 都是“结果未确认”，只用原 ID `GET /api/attention/actions/:id` 回读。
- 提交传输 30 秒超时，不重发，改为按原 ID 回读。回读：`succeeded`/`failed` 定案；`running` 每 2 秒轮询，最多 30 次后转为「再次核对」（只读），保留原操作 ID；服务端 `unknown` 只接受精确正向证据（`GET /api/inbox/:id/draft-requests/:operationId` 的同一请求终态、同一 `operationId` 的推迟/忽略）定案，否则保持未确认、只读核对；404 记为“未找到”，只允许用户明确用**同一 ID、同一载荷**重试（服务端指纹去重），不自动提交，不换新 ID。
- 对可能已执行的操作（未找到/未确认）明确重试时，若本机保存失败，保持原未确认状态且不提交；首次提交保存失败才显示「未保存，未提交」。待提交状态在保存屏障和提交之前写入。
- 只有明确拒绝或确认失败后才允许新的请求（新 ID）。未决槽位在来源变化后仍保留并阻止同类新请求；旧绑定的成功回执不会让新请求显示为完成。
- 「查看任务」只在本操作回执返回的任务 ID 存在、且回执绑定等于当前请求时显示，并附任务自身状态；「查看草稿」只在规范数据有当前且未过期的草稿时显示。
- 详情草稿标签：回复草稿 / 旧草稿 / 候选草稿（Reply draft / Old draft / Candidate draft）。有绑定的起草走同一类型化操作；没有稳定请求绑定的记录不提供起草（保留重新判断、忽略和问问 CyberMe），不再有单独的直接 `/draft` 请求。Proposal 路径不变。
- 消息下的「展开聊聊」只把内容和问题放入输入框，不创建操作记录、不提交、不调用模型。
- （视觉复核记录）卡片在回执未确认时，若规范数据已有当前草稿，起草选项仍显示蓝色完成勾选图标，旁边却是「再次核对」，等于把未确认说成已完成。完成图标只用于已定案的「查看草稿」；进行中、未确认、需重试的动作显示普通选项圆圈。
- （复核记录）灵感在服务端已被忽略后，规范刷新会让消息下的动作整体消失；若该忽略操作仍未确认（进行中/未确认/未找到/未保存），唯一的核对或重试入口也随之消失。已关闭的灵感只保留这些未决回执各自的「再次核对」/「重试」（原 ID、原绑定，只读回读或用户明确按同一 ID 重试），不提供新的展开聊聊、推迟、转任务或忽略；定案后入口随之消失。
- 自动流量只有 GET；渲染、聚焦和回读不提交、不外发、不调用模型。
